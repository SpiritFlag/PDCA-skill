# PDCA Design (pdca-skill v1)

이 세션은 design 문서 하나만 쓴다. 독자는 **맥락 없는 Do 세션**이다. 이 문서만 읽고 질문 파일 없이 끝까지 구현할 수 있어야 한다. 그 기준으로 빠진 것을 찾는다.

> **공통 규칙**
> - 서버 접근은 `npx pdcaw@1 … --json`뿐이다. MCP 툴을 부르지 않는다. (이 단계는 보통 서버가 필요 없다.)
> - 문서는 디스크에서 읽는다.
> - 사용자는 "사용자"다. 링크 금지. 요약 절 금지. 헤더 값은 교체, 이력은 Version History에.
> - 판단이 갈리는 것은 질문으로 남긴다.

---

## 0. 사이클 식별

- `git branch --show-current`가 `{버전}-{사이클명}` 형태면 그것이 사이클이다. 폴더는 `docs/PDCA/v{major}/{stem}/`.
- 그 형태가 아니면 인자로 버전을 받아 `docs/PDCA/*/{버전}-*/`를 찾는다. 없으면 멈춘다.

## 1. 게이트

- `{stem}.plan.md` 헤더 상태가 `확정`이어야 한다. 아니면 "plan이 확정되지 않았다. `/pdca-plan` 세션에서 확정한 뒤 다시 연다"고 말하고 멈춘다.
- `{stem}.design.md`가 이미 있으면 새로 만들지 않고 검수 루프(§6)로 들어간다.

## 2. 읽기

1. plan 전체. §2 범위 · §4 FR · §5 SC(검증 수단 열까지) · §3 실측을 기억한다.
2. `docs/RULE.md`의 검증 수단 목록. 배치 검증 방법은 이 목록 안에서만 고른다.
3. 변경이 닿을 코드를 직접 읽는다. 시그니처 · 스키마 · 기존 테스트의 단언 내용까지. plan §3 실측이 있어도 설계에 필요한 만큼 더 읽는다.

## 3. 골격

같은 폴더의 `design.template.md`를 `docs/PDCA/v{major}/{stem}/{stem}.design.md`로 복사한다. 헤더를 plan과 같은 값으로 채우고(상태 `초안`) `> 지침` 블록은 지운다.

## 4. 작성 순서

1. **§1.1 결정 지점** — 이 사이클에서 정해야 하는 것을 D-n으로 전부 나열한다. 갈림길이 없는 것은 "이렇게 한다 — 이유 한 줄"로 그 자리에서 끝낸다.
2. **§1.2 갈림길 상세** — 갈림길인 D-n에만. 선택지는 실재하는 만큼(둘이면 둘, 넷이면 넷). 채택하지 않을 안을 비교용으로 세우지 않는다. 각 선택지의 대가를 적고 추천 하나와 이유 두 줄. 진짜 동률이면 "동률"이라 쓰고 사용자가 고르게 둔다. 고정 3안(최소/클린/절충) 같은 틀을 쓰지 않는다.
3. **§2.1 파일** — 신설 · 수정 · 삭제와 책임, 관련 D. **테스트 파일도 여기 올린다.** 동작이 바뀌어 깨질 기존 테스트는 "수정"으로 미리 지목한다. 여기 없는 테스트는 Do가 고칠 수 없다.
4. **§2.2 인터페이스** — 시그니처 · 스키마 · 이벤트 · 설정 키를 코드 수준으로. Do가 이름을 짓지 않게.
5. **§3 구현 배치** — B-n. 3~5파일 단위, 의존 순서. 배치를 세션 하나 분량의 **모듈**(케밥 이름)로 묶는다. 배치마다 검증 방법: 명령 또는 확인 절차와 기대 결과, "어느 테스트가 무엇을 단언하나". 관련 SC를 붙인다. **plan의 SC 전부가 어느 배치의 검증에든 걸려야 한다.** 안 걸리는 SC가 있으면 배치를 추가하거나 §4에 적는다.
6. **§4 열린 질문** — 이 문서가 답하지 못한 것. 확정 시점에 "없음"이어야 한다.
7. **Version History** — `0.1 | 날짜 | 초안 | Plan 확정`.

## 5. 자기 점검, 커밋, 보고

쓰고 나서 처음부터 한 번 읽으며 묻는다.
- plan을 다시 쓰고 있는 절이 있나(목적 · 배경 · 원칙 · 요구사항 재진술). 있으면 지운다.
- 프로젝트 상수(계층 규칙 · 네이밍 · import 순서 · 환경변수)를 쓰고 있나. 있으면 지운다.
- Sonnet이 이걸 들고 첫 배치를 시작할 때 무엇을 물어볼까. 그 답을 §2에 넣는다.
- refine 사이클이면 한 페이지 안팎이 정상이다. 짧다고 채우지 않는다.

```
git add docs/PDCA/v{major}/{stem}/{stem}.design.md
git commit -m "design: {stem} 초안"
```

보고는 경로 한 줄 + 갈림길 D-n 목록(사용자가 검수에서 볼 지점) + 웹 검수 안내. 본문을 대화에 출력하지 않는다. **여기서 멈춘다.**

## 6. 검수 루프

의견을 붙여넣으면 반영 → Version History 행("웹 검수 의견 반영") → 갱신일 → 커밋 → 반영한 절 보고.

"확정"이면:
1. §4 열린 질문이 비어 있는지 확인한다. 남아 있으면 확정하지 않고 그 질문을 사용자에게 다시 묻는다.
2. 갈림길 D-n에 "사용자 선택 대기"가 남아 있으면 같은 처리.
3. 헤더 상태 `확정`, 갱신일, Version History `사용자 검수 확정` 행. 커밋 · 푸시.
4. "확정됐다. 다음은 새 세션에서 `/pdca-do`"라고 한 줄 보고하고 끝낸다.

## 하지 않는 것

- 코드를 수정하지 않는다. 구현을 시작하지 않는다. 테스트를 쓰지 않는다.
- plan을 고치지 않는다. plan이 틀렸으면 그 사실을 사용자에게 말하고 plan 세션으로 돌려보낸다.
- 진행 기록 · 구현 결정을 여기 쓰지 않는다. 그건 do 문서다.
- 고정 개수 선택지, 전체를 묶는 단일 추천안, 합산 점수를 쓰지 않는다.
- 통합 브랜치 · `main` · 백로그를 건드리지 않는다.
