# PDCA Plan (pdca-skill v1)

이 세션은 plan 문서 하나만 쓴다. 독자는 사용자다. 읽고 "이 범위에 시간을 쓴다 / 안 쓴다"를 정할 수 있어야 한다.
설계(어떻게)는 design의 일이고, 여기 쓰지 않는다.

> **공통 규칙**
> - 서버 접근은 `npx --no-audit -y pdcaw@1 … --json`뿐이다. MCP 툴을 부르지 않는다.
> - 문서는 디스크에서 읽는다. 서버에서 문서를 내려받지 않는다.
> - 문서 안에서 사용자는 "사용자"다. 마크다운 링크를 쓰지 않는다. 요약 절을 두지 않는다. 헤더 값은 교체하고 이력은 Version History에만 남긴다.
> - 판단이 갈리는 것은 바꾸지 말고 번호 매긴 질문으로 남긴다.

## 0. 인자

`/pdca-plan <버전> <사이클명> ["직접 지시 문장"]`

- 버전: `vX.Y.Z`. 아니면 멈춘다.
- 사이클명: `<종류>-<대상>` 케밥. 종류는 `explore` `adopt` `enhance` `refine` 중 하나. `fix`는 패치 트랙이라 plan을 쓰지 않는다 — "패치는 브랜치를 파서 고치고 `/pdca-close`로 닫는다"고 안내하고 멈춘다.
- 직접 지시 문장이 있으면 백로그 없이 시작하는 사이클이다.
- 어간(stem) = `{버전}-{사이클명}`. 브랜치명 · 폴더명 · 파일 어간이 전부 이것이다.

## 1. 준비

1. `.pdcarc.json`이 레포 루트에 있는지 본다. 없으면 프로젝트를 물어보고 멈춘다.
2. `docs/RULE.md`를 읽는다. 검증 수단 목록 · 통합 브랜치 이름(기본 `develop`) · CI 확인 명령 · 예외를 기억한다.
3. 버전 충돌 검사. 둘 다 본다.
   - `git tag`에 같은 버전이 있으면 멈춘다.
   - `npx --no-audit -y pdcaw@1 cycle list --json`에 같은 버전이 있으면 멈춘다. 서버에 예약된 미래 버전이 있으면 그 사다리를 존중해 사용자에게 알린다.
4. 같은 사이클명이 최근에 있었으면(`docs/PDCA/*/*-{사이클명}/`) 한 줄 알린다. 막지는 않는다 — 열쇠는 버전이다.
5. 작업트리가 깨끗한지, 통합 브랜치 최신인지 확인한다. 아니면 사용자에게 알리고 지시를 기다린다.

## 2. 브랜치 · 폴더

```
git switch -c {stem} {통합 브랜치}
mkdir -p docs/PDCA/v{major}/{stem}
```

- 메이저 폴더는 `v{N}`뿐이다. 코드네임은 `docs/PDCA/_INDEX.md`의 절 제목에만 둔다.
- 같은 폴더의 `plan.template.md`를 `docs/PDCA/v{major}/{stem}/{stem}.plan.md`로 복사해 골격을 만든다. 헤더를 채우고 `> 지침` 블록은 지운다. 상태는 `초안`.

## 3. 재료

- **백로그**: 범위에 들어갈 항목마다 `npx --no-audit -y pdcaw@1 backlog get <id> --json`으로 detail을 끝까지 읽는다. detail이 다른 문서(`v0.13.2 report §5.3` 등)를 가리키면 그 원문까지 로컬에서 읽는다. 제목만 보고 범위를 정하지 않는다.
- **직전 사이클 report**: `docs/PDCA/` 아래 버전이 가장 높은 폴더의 `*.report.md`. §3(미완료) · §5.3(Try) · §7(후보)을 읽는다.
- **코드**: 범위가 건드릴 파일 · 함수 · 스키마 · 설정을 직접 읽는다. 이것이 §3 실측의 재료다.
- 직접 지시 사이클이면 백로그 대신 사용자의 문장이 재료다. 문장이 모호하면 §5 SC를 쓰기 전에 질문한다.

## 4. 작성 순서

골격을 먼저 만들었으니 절 하나씩 채운다. 한 번에 통째로 쓰지 않는다.

1. **§1 목적** — 한 단락. 백로그 항목 문장을 인용한다. 선행 사이클과의 관계. 개정 때 늘리지 않고 다시 쓴다.
2. **§2 범위** — 포함은 백로그 id로 세어 N건 고정(직접 지시면 "직접 지시" + 문장). 제외는 인접해서 손대고 싶어질 것을 미리 열거. 발견 시 처리는 템플릿 문구 그대로.
3. **§3 실측** — F-n. 추정 금지. 파일 · 함수 · 스키마를 읽어 확정한 사실만, 근거 경로를 인라인 코드로. 성패를 가르는 것은 ★. 지원 여부가 불확실하면 "지원하지 않으면 우회 비용"까지. 이 영역을 덮는 기존 테스트가 있으면 F-n으로 적는다.
4. **§4 요구사항** — FR-n. 범위 항목과 매핑.
5. **§5 성공 기준** — SC-n. 실증 가능한 문장. 검증 수단은 RULE.md 목록에 있는 것만. 사용자 육안이 많으면 절 끝에 그 사실을 한 줄.
6. **§6 리스크** — R-n과 대응.
7. **§7 직전 Try 이행** — 직전 report §5.3의 Try마다 "적용: 어디에" 또는 "해당 없음: 이유". 직전 사이클이 없으면 절을 지운다.
8. **Version History** — `0.1 | 날짜 | 초안 | 사이클 시작`.

## 5. 초안 커밋과 보고

```
git add docs/PDCA/v{major}/{stem}/{stem}.plan.md
git commit -m "plan: {stem} 초안"
```

사이클 브랜치에서는 문서를 자유롭게 커밋한다. 통합 브랜치에는 close가 머지 커밋 하나로 넣는다.

보고는 문서 경로 한 줄과 "웹 클로드에 옮겨 검수하고, 의견을 여기 붙여넣으면 반영한다. '확정'이라 하면 상태를 확정으로 바꾸고 이 세션을 끝낸다"뿐이다. 본문을 대화에 다시 출력하지 않는다. **여기서 멈춘다.**

## 6. 검수 루프

사용자가 의견을 붙여넣으면:

1. 의견을 해당 절에 반영한다. 범위가 넓어지면 §2.1 N건을 다시 세고 명시한다.
2. Version History에 행을 추가한다. 계기 열은 "웹 검수 의견 반영".
3. 헤더 갱신일을 오늘로 교체한다.
4. 커밋한다. 반영한 절 이름만 보고한다.

사용자가 "확정"이라 하면:

1. 헤더 상태를 `확정`, 갱신일을 오늘로.
2. Version History에 `사용자 검수 확정` 행.
3. 커밋 · 푸시한다.
4. "확정됐다. 다음은 새 세션에서 `/pdca-design`"이라고 한 줄 보고하고 세션을 끝낸다.

## 하지 않는 것

- 코드를 수정하지 않는다. 설계를 쓰지 않는다. design 세션을 여기서 시작하지 않는다.
- 통합 브랜치 · `main`을 건드리지 않는다. 백로그 상태를 바꾸지 않는다.
- 요약 절, Context Anchor, 아키텍처 선택표, 프레임워크 비교, 컨벤션, 환경변수 표를 쓰지 않는다.
- 사이클명이 겹친다고 막지 않는다. 알리기만 한다.
- 이 대화에서만 통하는 지시대명사를 문서에 쓰지 않는다. PAT · 토큰 · 개인정보를 예시에 넣지 않는다.
