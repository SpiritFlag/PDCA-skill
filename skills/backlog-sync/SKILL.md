# 백로그 동기화 (pdca-skill v1)

닫힌 사이클을 기준으로 백로그를 실상에 맞춘다. 순서를 그대로 따른다.

> **이 절차의 두 축**
> ① 이번 사이클이 만든 변화를 반영한다(§3~§6)
> ② 이번 사이클과 무관하게 **썩어가는 항목**을 걸러낸다(§7)
> ②가 없으면 보드는 반드시 쌓이기만 한다.

> **공통 규칙**
> - 서버 접근은 `npx pdcaw@1 … --json`뿐이다. MCP 툴을 부르지 않는다.
> - 문서는 디스크에서 읽는다. 사용자는 "사용자"다.
> - `dropped`와 `todo` 복원은 사람 전용이다. CLI도 `todo`를 거부한다.

---

## 0. 프로젝트 · 사이클 확정

- 프로젝트: `.pdcarc.json`의 `projectId`. `npx pdcaw@1 project list --json`으로 이름을 확인해 밝힌다. 없으면 후보를 나열하고 사용자가 고른다.
- 사이클: `/pdca-close`에서 불렸으면 방금 닫은 버전. 단독 실행이면 현재 브랜치 `{버전}-{사이클명}`에서 읽고, 그것도 아니면 `npx pdcaw@1 cycle list --json`에서 **가장 최근에 만들어진** 버전(`createdAt` 기준, 가장 높은 버전이 아니다 — 예약 버전이 있을 수 있다)을 후보로 한 줄 확인받는다.
- 완료일 = 태그 날짜(`git log -1 --format=%cs {버전}`). 이후 `closedOn` · `openedOn`에 쓴다.

## 1. 근거

- **report**: `docs/PDCA/*/{버전}-*/{stem}.report.md`를 디스크에서 읽는다. 판정이 갈리는 항목이 있으면 같은 폴더의 `analysis.md`도. 서버에서 내려받지 않는다.
- **백로그 전건**: `npx pdcaw@1 backlog list --json` — 상태 필터 없이. 열린 것만 보면 닫힌 항목과의 중복 생성을 놓친다. 요약이라 detail은 없다 — 판단에 필요한 항목만 `npx pdcaw@1 backlog get <id> --json`으로 읽는다.

## 2. 대조 대상 뽑기

report §2 완료 항목(백로그 id), §3.1 이월, §3.2 보류, §3.3 폐기 후보, §3.4 범위 밖 발견, §5.3 Try, §6 프로세스 · 도구 개선, §7 후보. 여덟 곳이다. 셋만 보면 빠진다.

## 3. 종료 상태 갈라 찍기

| 상태 | 조건 |
|---|---|
| `done` | 이 사이클이 **겨냥해서** 해결한 항목(report §2) |
| `resolved` | 의도치 않게 딸려 해결됐거나 필요 자체가 사라진 항목 |
| `dropped` | **사람 전용.** 스스로 찍지 않는다 — §8 질문으로 |
| `todo` 복원 | **사람 전용.** 요청하지 않는다 |

- **부분 해결은 닫지 않는다.** 항목이 갈래 여럿을 담고 있고 일부만 처리됐으면 §6 축소로 기록한다. "대체로 됐으니 닫자"는 금지.
- report 서술만 믿지 않는다. 백로그 원안(detail)이 요구한 범위와 대조한다. 원안이 A · B를 요구했는데 report가 A만 말하면 부분 해결이다.

```
npx pdcaw@1 backlog update <id> --status done --closed-on <완료일> \
  --append-detail "[<완료일> 완료 — 근거: <버전> <SC/FR/§ 번호>. <왜 그렇게 판정했는지 한두 문장>]" --json
```

## 4. detail 갱신 — 원안 보존

`--append-detail`은 서버가 기존 본문 앞에 블록을 얹는다. 원안은 그대로 남는다. `--detail`(전체 교체)은 쓰지 않는다.

블록 형식: `[YYYY-MM-DD 완료|해소|축소|갱신|등록 — 근거: <버전> <SC/FR/§ 번호>]` 뒤에 한두 문장.

- **왜 그렇게 판정했는지** 적는다. 상태만 바꾸면 다음 사람이 되짚을 수 없다.
- 처리 방식이 원안과 달라졌으면 명시한다(예: "원안의 ⓐ/ⓑ가 아니라 ⓒ로 해결").
- 관련 항목은 **id 앞 8자로 교차 참조**한다.

## 5. 신규 항목 생성

| 출처 | 처리 |
|---|---|
| §3.1 이월 | 기존 항목이 있으면 갱신, 없으면 신규 `todo` |
| §3.2 보류 | 위와 같되 제목 끝에 착수 조건(예: "— M4 이후 착수"), detail에 조건을 적는다 |
| §3.3 폐기 후보 | **생성하지 않는다.** 기존 항목이면 상태를 바꾸지 말고 §8 질문으로 |
| §3.4 범위 밖 발견 | 신규 `todo`. 위치(경로)를 detail에 |
| §5.3 Try | 아래 특칙 |
| §6 프로세스 · 도구 개선 | 소관이 이 프로젝트면 신규. 스킬 · CLI · 서버 소관이면 그 프로젝트 백로그 대상이라 **여기 만들지 않고** §8 질문으로 올린다 |
| §7 후보 | 이미 있는지 확인 후 신규 |

- **생성 전 반드시 중복 확인.** §1 전건과 제목 · detail을 대조한다. 있으면 그 항목을 `[… 갱신]`으로.
- **Try 특칙**: 사이클마다 신규 생성하지 않는다. 체크리스트 · 규율 계열의 **누적 항목**이 있으면 그 detail에 `(a)(b)(c)…` 라벨을 이어 붙인다. 없을 때만 신설.
- `--opened-on <완료일>`. detail 끝에 출처 `(<버전> report §<번호>)`.

```
npx pdcaw@1 backlog create --title "<제목>" --priority <p> --opened-on <완료일> --detail-file <임시파일> --json
```

## 6. 전제가 바뀐 기존 항목 재평가

이번 사이클로 근거 · 범위가 달라진 항목은 **상태를 바꾸지 말고** `[… 축소]` 또는 `[… 갱신]`만 append한다.

- 축소: 갈래 일부의 전제가 소멸. **무엇이 남았는지** 명시.
- 갱신: 착수 조건 · 소관 · 처리 방법이 달라짐. 선행 조건이 충족됐으면 "이제 착수 가능"은 중요한 상태 변화다.

## 7. 정체 항목 스윕 ★ 이 절차의 절반

```
npx pdcaw@1 backlog list --stale 14 --json
```

1. 각 항목을 `backlog get`으로 읽어 detail의 **착수 조건 · 선행 항목 · 전제**가 그 사이 충족되거나 소멸했는지 대조한다. 대조 대상은 그 항목이 가리키는 report와 백로그 id다.
2. 셋으로 가른다.

| 판정 | 처리 |
|---|---|
| 여전히 유효 | `[… 갱신]` — 착수 조건 현행화 |
| 이미 해소된 듯 | **닫지 말고** §8 질문 |
| 전제 소멸 | **폐기하지 말고** §8 질문 |

- 근거 없이 판단하지 않는다. "오래됐으니 죽었겠지"는 금지. 대조할 문서가 없으면 그 사실을 질문에 적는다.
- 정체 건수가 20건을 넘으면 상위 몇 건만 훑고 그 사실을 보고에 밝힌다. 나머지는 별도 세션 제안.

## 8. 판단 보류

다음은 **바꾸지 말고 질문으로 남긴다.** 질문은 "닫아도 되는지 묻는 형태"로, 판단 재료(원안이 요구한 것 / 실제 처리된 것)를 같이.

- `done`인지 `resolved`인지 갈리는 항목
- 원안 범위 중 일부만 충족된 항목
- 여러 건이 묶여 통째로 닫을 수 없는 항목
- 폐기 여부가 걸린 항목(report §3.3, §7 산출 포함)
- 다른 프로젝트 소관인 개선 제안(§6)
- report 서술과 백로그 원안이 어긋나는 항목

## 9. 보고

1. 프로젝트 · 버전 · 사이클명 · 완료일 한 줄.
2. 처리 요약 표 — `done` / `resolved` / 신규 / 갱신 구획에 제목 한 줄씩(id 앞 8자).
3. 보드 집계(상태별 건수).
4. **스윕 결과 한 줄**: 14일 이상 정체 건수, 이번에 손댄 건수, 남은 건수.
5. 판단이 갈린 곳이 있으면 왜 그렇게 찍었는지 짧게.
6. §8 질문을 번호 매겨 따로.

## 하지 않는 것

- 보고서 서술만 믿고 닫지 않는다. 부분 해결을 닫지 않는다.
- 정체 항목을 임의로 닫거나 버리지 않는다. `dropped` · `todo` 복원을 스스로 찍지 않는다.
- `--detail`로 전체 교체하지 않는다(원안 소실). `--append-detail`만.
- 사이클 밖 사실(대화 중 나온 발견 · 신규 버그)을 이 절차에 섞지 않는다. 굳이 함께 처리했다면 보고에서 구분해 밝힌다.
- 다른 프로젝트 백로그에 쓰지 않는다.
