# PDCA Close (pdca-skill v1)

이 세션이 Act 전체다. 감사 → 보고 → 릴리즈노트 → 인덱스 → 머지 · 태그 → 업로드 → main → 백로그. 비가역 단계(푸시 · 태그 · main 전진)는 매번 사용자 확인을 받는다.

> **공통 규칙**
> - 서버 접근은 `npx pdcaw@1 … --json`뿐이다. MCP 툴을 부르지 않는다.
> - 문서는 디스크에서 읽는다. 사용자는 "사용자"다. 링크 금지. 합산 수치 · 점수 · 비율을 만들지 않는다.
> - 판단이 갈리는 것은 질문으로 남긴다. 폐기 · 버전 변경은 사용자만 정한다.

---

## 0. 모드 판정

- `git branch --show-current` = `{버전}-{사이클명}`. 여기서 버전 · 사이클명 · 어간(stem)을 읽는다. 폴더 `docs/PDCA/v{major}/{stem}/`.
- 폴더에 `{stem}.plan.md`가 있으면 **사이클 모드**. 없으면 **패치 모드**(§2 · §3 생략).
- 패치인데 브랜치가 `{버전}-fix-…` 형태가 아니면: `git describe --tags --abbrev=0`의 patch를 +1한 버전을 제안해 확인받고, `git switch -c {버전}-fix-{대상}`과 폴더를 만든다. 대상 이름은 사용자에게 받는다.
- `docs/RULE.md`를 읽는다. 통합 브랜치 · 릴리즈 브랜치 이름, CI 확인 명령, 종료 훅, 릴리즈노트 톤 · 이모지 · 제품명.

## 1. 게이트

전부 통과해야 시작한다. 하나라도 아니면 무엇이 막는지 말하고 멈춘다.

| 조건 | 확인 |
|---|---|
| (사이클) do 전 배치 `검증 완료` | `{stem}.do.md` §1 |
| (사이클) 질문 파일 없음 | `ls docs/PDCA/v{major}/{stem}/*.q*.md` 가 비어야 함 |
| 작업트리 깨끗함, 브랜치 푸시됨 | `git status`, `git log @{u}..` |
| 브랜치 CI 초록 | RULE.md의 CI 확인 명령. 없으면 사용자에게 "CI 초록 확인했나"를 묻고 답을 받는다 |
| 버전 충돌 없음 | `git tag`에 없음, `npx pdcaw@1 cycle list --json`에 없음 |

## 2. analysis (사이클 모드)

같은 폴더의 `analysis.template.md`로 `{stem}.analysis.md` 골격을 만든다. 이 문서는 **처음 검증하는 문서가 아니라 do의 주장을 감사하는 문서**다.

1. **§1 SC 판정** — plan §5의 SC마다:
   - do §3에서 그 SC를 덮는 검증 기록을 찾아 "do 근거" 열에 `Do §3 B-n …`으로 적는다. 없으면 "없음".
   - 자동 테스트가 근거면 **테스트 파일을 열어 그 SC를 실제로 단언하는지 읽는다.** 존재만으로 실증이 아니다. 그 뒤 명령을 독립 재실행한다.
   - 사용자 육안이 근거면 do §3의 날짜 · 내용을 확인하고 "재확인 불가(사용자 확인 신뢰)"로 적는다.
   - 판정: `실증` / `부분 실증(무엇이 빠졌나)` / `미실증(사유)` / `범위 변경(→ report §3.n)`. 합산하지 않는다.
2. **§2 결정 이행** — design §1.1의 D-n마다 코드를 대조해 지켰는지, 어긋났으면 어디서 어떻게.
3. **§3 결함** — 감사 중 발견한 것을 I-n으로. 이 사이클 범위 안이면 **즉시 수정 + 그 결함을 잡았을 회귀 테스트 + 재검증**, 결과를 재검증 열에. 범위 밖이거나 크면 이월(report §3.1)로 표시. 수정한 것은 커밋한다.
4. **§4 감사 방법** — 직접 실행한 것 / do 기록을 신뢰한 것 / 감사 범위 밖.
5. `> 지침` 블록을 지우고 Version History `0.1 | 날짜 | 감사 | Do 전 배치 검증 완료`. 커밋.

## 3. report (사이클 모드)

`report.template.md`로 `{stem}.report.md` 골격. 절 번호는 backlog-sync가 읽으므로 바꾸지 않는다.

1. **§1 결과** — 한 단락. 무엇이 됐고 무엇이 안 됐나. SC는 "Analysis §1 참조"라고만.
2. **§2 완료 항목** — plan §2.1 범위 대비, 산출물 경로.
3. **§3 미완료 항목** — 넷으로 가른다. 섞지 않는다.
   - 3.1 이월: 할 것이다, 이번엔 못 했다. 사유.
   - 3.2 보류: 조건이 충족되면 한다. 착수 조건.
   - 3.3 폐기 후보: 하지 않는 게 맞아 보인다. 이유. **여기 적기만 하고 백로그를 바꾸지 않는다.**
   - 3.4 범위 밖 발견: do §5 진행 로그와 analysis §3에서 이월된 것.
4. **§4 결정과 결과** — D-n별 결과. 뒤집힌 결정은 왜.
5. **§5 회고** — Keep / Problem / Try. Try는 다음 plan §7이 이행을 확인하므로 실행 가능한 문장으로.
6. **§6 프로세스 · 도구 개선** — 반복 비용이 관측된 것만. 고칠 곳(스킬 / RULE / CLI / 서버)을 지목.
7. **§7 다음 사이클 후보**.
8. 지침 블록 삭제, Version History, 커밋.

## 4. release (공통)

`release.template.md`로 `{stem}.release.md`. 헤더 표와 Version History가 없는 유일한 문서다.

- 재료: report(사이클 모드), `git diff $(git describe --tags --abbrev=0)..HEAD --stat` 과 주요 파일 diff, do §3 검증 기록, **직전 release** — `docs/PDCA/` 아래 버전이 바로 아래인 폴더의 `*.release.md`(연속성 판단용).
- 제목 이모지 · 톤 · 제품명은 RULE.md 릴리즈노트 절. 비어 있으면 `.pdcarc.json`의 프로젝트명과 템플릿 기본 톤.
- 규칙: report의 주장은 diff와 대조해 **확인된 것만** 쓴다. 해당 없는 카테고리는 섹션을 지운다. 문장은 "-습니다" 체. 내부 식별자 · 파일명 대신 동작과 효익. 직전 release에 이미 나간 내용은 제외하거나 "마무리" 맥락으로만. 다부작이면 intro · outro에 시리즈 내 위치. outro는 규모를 반영.
- 템플릿 끝의 HTML 주석을 지운다. 커밋.

## 5. 인덱스

`docs/PDCA/_INDEX.md`의 `## v{major}` 절 표 **맨 위**에 행을 추가한다. 절이 없으면 파일 맨 위에 새 절을 만든다(코드네임은 사용자에게 묻는다).

`| 버전 | 날짜 | 사이클명 | 종류 | 한 줄 요약 | 문서 |` — 종류는 사이클명 접두어. 한 줄 요약은 결과만, 60자 내외, 수치 최대 2개, 인라인 코드 최대 1개, 이월 · 후속 언급 금지. 문서 열은 존재하는 stage를 ` · `로(패치는 `release`). 링크 없음.

## 6. 종료 훅

RULE.md 종료 훅 목록을 순서대로 실행한다(README 갱신, 버전 파일 수정 등). 훅이 "없음"이면 건너뛴다.

## 7. 브랜치 커밋 · CI

```
git add -A && git commit -m "close: {stem} 문서 · 인덱스 · 훅"
git push
```
CI 확인 명령이 있으면 초록을 확인한다. 없으면 사용자에게 묻는다.

## 8. 머지 · 태그 (확인 필요)

사용자에게 "통합 브랜치에 머지하고 태그를 푸시한다"를 묻고 답을 받은 뒤:

```
git switch {통합}
git pull --ff-only
git merge --no-ff {stem} -m "merge: {stem}"
git tag -a {버전} -m "{사이클명} — {인덱스 한 줄 요약}"
git push origin {통합} {버전}
git rev-parse {버전}^{}   # 머지 커밋 SHA와 같아야 한다
```

## 9. 업로드

```
npx pdcaw@1 upload --version {버전}
```
릴리즈 생성(있으면 재사용) + 변경 문서 업로드 + release.md를 릴리즈노트로. 실패하면 출력을 그대로 보고하고 §10으로 가지 않는다.

## 10. 릴리즈 브랜치 전진 (확인 필요)

통합 브랜치 CI가 초록인지 확인한다(명령 또는 사용자). 초록이면 사용자에게 묻고 RULE.md의 전진 방식대로 한다.

- `ff-only`:
  ```
  git switch {릴리즈}
  git merge --ff-only {버전}
  git push origin {릴리즈}
  ```
- `PR merge commit`(main 직푸시 금지 프로젝트):
  ```
  gh pr create --base {릴리즈} --head {통합} --title "release: {사이클명} {버전}"
  gh pr checks <PR>          # 통과 확인
  # 사용자 확인 후 Merge commit으로 병합 (Squash · Rebase 금지)
  git switch {통합} && git fetch origin && git merge origin/{릴리즈} && git push origin {통합}
  git branch -a --contains {버전}   # main · develop 둘 다 나와야 한다
  ```

빨가면 릴리즈 브랜치를 건드리지 않고 "패치 트랙으로 잇는다: `git switch -c {patch버전}-fix-{대상} {통합}`"을 안내한다. 태그는 되돌리지 않는다.

## 11. 백로그 동기화

`backlog-sync` 스킬의 절차를 이 세션에서 그대로 수행한다. 대상 사이클은 방금 닫은 버전. 패치 모드면 그 패치가 백로그 항목에서 나왔는지 사용자에게 묻고, 나왔으면 그 항목만 done 처리한다.

## 12. 보고

- 버전 · 사이클명 · 태그 SHA · 업로드 결과 · main 전진 여부를 한 줄씩.
- report §3.3 폐기 후보와 backlog-sync의 판단 보류를 번호 매겨 따로.
- 다음 사이클 후보(report §7)를 한 줄.

## 하지 않는 것

- 버전을 임의로 바꾸지 않는다(충돌이면 멈추고 묻는다). 폐기를 스스로 찍지 않는다.
- 확인 없이 머지 · 태그 · main 푸시를 하지 않는다. 태그를 되돌리지 않는다.
- 테스트를 끄거나 건너뛰어 초록을 만들지 않는다. 감사 결함을 수정할 때 회귀 테스트 없이 넘어가지 않는다.
- Match Rate · 합산 점수 · 비율을 쓰지 않는다. 문서 간 링크를 쓰지 않는다.
- report 절 번호를 바꾸지 않는다. release에 확인되지 않은 기능을 쓰지 않는다.
