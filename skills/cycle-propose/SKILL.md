# 사이클 제안 (pdca-skill v1)

열린 백로그에서 함께 처리하면 이득인 항목을 묶어 후보 2~3안을 만들고 사용자가 고르게 한다. **제안까지만 한다.** 읽기 전용이다.

> **공통 규칙**
> - 서버 접근은 `npx --no-audit -y pdcaw@1 … --json`뿐이다. MCP 툴을 부르지 않는다.
> - 문서는 디스크에서 읽는다. 사용자는 "사용자"다.

---

## 0. 프로젝트 확정

- `.pdcarc.json`의 `projectId`가 대상이다. `npx --no-audit -y pdcaw@1 project list --json`으로 이름을 확인해 첫 줄에 "프로젝트: {워크스페이스}/{프로젝트}"로 밝힌다.
- `.pdcarc.json`이 없으면 `project list` 결과를 나열하고 사용자가 고르게 한다. 추측으로 진행하지 않는다.

## 1. 재료

1. `npx --no-audit -y pdcaw@1 backlog list --json` — 전 상태 요약. 후보는 `todo`에서만 고르되, 닫힌 항목은 "이미 해결된 것 아닌가"를 판정하는 근거로 쓴다.
2. 후보로 올릴 항목은 `npx --no-audit -y pdcaw@1 backlog get <id> --json`으로 detail을 **끝까지** 읽는다. detail이 문서를 가리키면(`v0.13.2 report §5.3` 등) 그 원문을 `docs/PDCA/` 아래에서 찾아 읽는다. 제목만 보고 묶지 않는다.
3. 직전 사이클 report — `docs/PDCA/` 아래 버전이 가장 높은 폴더의 `*.report.md`. §3(이월 · 보류)과 §5.3(Try), §7(후보)을 읽는다.
4. 버전 사다리 — `git tag`와 `npx --no-audit -y pdcaw@1 cycle list --json`. 서버에 예약된 미래 버전이 있으면 존중한다.
5. `docs/PDCA/_INDEX.md`의 메이저 절 제목(현재 메이저와 코드네임).

## 2. 묶는 기준

아래 중 하나로 설명되지 않으면 같은 사이클에 넣지 않는다. "둘 다 급하니까"는 근거가 아니다.

- **같은 접점** — 같은 파일 · 모듈 · 스키마 · 씬을 건드린다.
- **선후 의존** — A를 해야 B가 가능하다.
- **같은 도입에 딸린 전후 작업** — 외부 도구 · 라이브러리 도입 하나에 붙는 준비 · 전환 · 정리.
- **같은 검증 수단** — 한 번의 실측 · 한 번의 육안 확인으로 같이 검증된다.

묶음 크기는 3~5건이 기본. 6건을 넘으면 쪼갠다. 1건짜리 안은 성격이 확연히 다를 때만.

## 3. 사이클명 · 트랙 · 버전

- 형태 `<종류>-<대상>` 케밥. 종류: `explore`(새 영역 탐색) · `adopt`(외부 도입) · `enhance`(기존 기능 개선) · `refine`(이월 마감 · 정리) · `fix`.
- **`fix`는 사이클이 아니라 패치 트랙이다.** 설계가 필요 없는 수정은 후보에 넣지 않고 "패치로 바로: 브랜치 파서 고치고 `/pdca-close`"로 따로 나열한다.
- 종류가 둘에 걸치면 지배적인 하나. 못 고르면 응집도가 낮은 것이니 쪼갠다.
- 사이클명은 유일할 필요가 없다(열쇠는 버전). 같은 이름이 `docs/PDCA/*/*-{이름}/`에 이미 있으면 "그때 뭘 했는지" 한 줄로 상기시킨다.
- 버전 제안: 최신 태그 기준 **minor +1**(`refine` `enhance` `adopt` `explore` 전부). major는 사용자가 새 시대를 열 때만이라 제안하지 않는다. 예약 버전과 부딪히면 그 다음 번호.

## 4. 후보 2~3안 — 안마다 아래 7개

1. **사이클명 · 버전 · 한 줄 목적** — 왜 지금 이걸 묶는가
2. **포함 항목** — 제목 + id 앞 8자, 번호로 세어 N건 고정
3. **묶은 근거** — §2 기준 중 어느 것인지 이름으로
4. **선행 조건** — 다른 백로그 · 외부 결정에 막혀 있으면 그 이름
5. **불확실 지점 ★** — 착수 전 실측이 필요한 것, 지원 여부를 모르는 것
6. **크기 감** — S / M / L 과 근거 한 줄
7. **직전 Try 반영** — 직전 report §5.3 Try 중 이 안에서 자연히 이행되는 것

안끼리는 다른 축이어야 한다. 같은 묶음을 이름만 바꿔 재배열한 것은 별개 안이 아니다.

## 5. 추천과 보류

- 하나를 "지금 추천"으로 지목하고 이유 두 줄. 선택은 사용자가 한다.
- 어느 안에도 못 들어간 열린 항목 중 2사이클 이상 묵은 것은 제목을 따로 밝힌다.
- 폐기 후보로 보이는 항목은 상태를 바꾸지 말고 질문으로.
- 직전 report §5.3 Try · §6 개선 제안 중 백로그에 없는 것이 있으면 밝힌다(backlog-sync 누락 가능성).

## 6. 출력

- 첫 줄: 프로젝트, 직전 사이클(버전 · 이름), 최신 태그.
- 후보 표: `안 / 사이클명 / 버전 / 포함 건수 / 크기 / 한 줄 목적`
- 안별 상세(§4의 7개).
- 패치로 바로 갈 항목 목록(있으면).
- 보류 · 질문을 번호 매겨 따로.
- 마지막 줄: "몇 번으로 갈지 골라줘. 고르면 새 세션에서 `/pdca-plan <버전> <사이클명>`으로 넘어간다."
- 앞뒤 설명은 한 줄 이내.

## 하지 않는 것

- 백로그 상태 변경 · 신규 생성 · 문서 작성 · 코드 수정 · 브랜치 생성. 전부 금지.
- major 버전 제안, `fix`를 사이클 후보로 올리기.
- PAT · 토큰 · 개인정보를 예시에 넣지 않는다. 이 대화에서만 통하는 지시대명사를 쓰지 않는다 — 사용자가 그대로 복사해 다음 세션에 넘길 수 있어야 한다.
