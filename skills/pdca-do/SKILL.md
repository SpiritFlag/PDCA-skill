# PDCA Do (pdca-skill v1)

이 세션은 코드와 do 문서를 쓴다. design은 읽기 전용이다. 검증은 여기서 한다 — do 문서 §3에 없는 것은 검증되지 않은 것이다.

> **공통 규칙**
> - 서버 접근은 `npx pdcaw@1 … --json`뿐이다(이 단계는 보통 필요 없다). MCP 툴을 부르지 않는다.
> - 문서는 디스크에서 읽는다. 사용자는 "사용자"다. 링크 금지. 헤더 값은 교체, 이력은 Version History에.
> - 코드는 평소처럼 커밋한다. do 문서도 이 브랜치에서 자유롭게 커밋한다.

## 0. 사이클 · 범위 식별

- `git branch --show-current` = `{버전}-{사이클명}`. 폴더 `docs/PDCA/v{major}/{stem}/`. 아니면 인자 버전으로 폴더를 찾고, 없으면 멈춘다.
- `--scope <모듈명>` 또는 `--scope B3,B4`. 없으면 do 문서 §1에서 첫 미착수 배치가 속한 모듈 전체.

## 1. 게이트와 do 문서

1. `{stem}.design.md` 헤더 상태가 `확정`이어야 한다. 아니면 멈춘다.
2. `{stem}.do.md`가 없으면 같은 폴더의 `do.template.md`로 만든다. 헤더를 채우고(상태 `진행 중`), §1 배치 현황을 design §3에서 복사한다(B-n · 모듈 · 하는 일, 상태 전부 `미착수`). `> 지침` 블록은 지운다. Version History `0.1 | 날짜 | 초안, 배치 현황 등재 | Design 확정`.
3. 이미 있으면 전체를 읽는다. §5 진행 로그 마지막 세션의 "다음 세션 주의점"을 먼저 본다. 이번 세션 번호 = 마지막 + 1.
4. `docs/RULE.md`의 검증 수단 목록과 테스트 명령을 읽는다.
5. §5에 `### 세션 N (날짜)` 을 열고 "시작: 맡은 배치, 읽은 것"을 적는다.

## 2. 배치 루프

범위의 배치를 design §3 순서대로 하나씩. **배치 하나를 끝까지(구현 + 검증) 하고 다음으로.** 넓게 뼈대만 치지 않는다.

1. §1 상태를 `진행 중`으로, 세션 번호 기입.
2. design §2 변경 지점과 §2.2 인터페이스대로 구현한다. 이름 · 시그니처는 design이 준 것을 쓴다.
3. design이 정하지 않은 세부를 정했으면 §2 구현 결정에 `무엇 / 어떻게 / 이유 / 관련 B·D`를 적는다. design을 **바꾸는** 결정은 여기가 아니라 §3 질문 파일이다.
4. 테스트: design §2.1이 신설 · 수정으로 지목한 테스트를 코드와 함께 쓴다. design에 없는 테스트를 추가했으면 §2에 이유. **design이 지목하지 않은 기존 테스트가 실패하면 그 테스트를 고치지 않는다 — 질문 파일이다.** skip · quarantine · 조건부 건너뛰기로 초록을 만들지 않는다. 불안정한 테스트를 발견하면 §2에 기록하고 그대로 둔다.
5. 검증: design §3의 검증 방법을 그대로 실행한다.
   - 자동 테스트: 명령과 결과(통과 수 / 실패 내용)를 §3에.
   - 사용자 육안: 무엇을 어디서 보면 되는지 정확히 적어 사용자에게 요청하고 **답을 기다린다.** 확인받으면 날짜와 함께 "확인"으로 §3에. 사용자가 못 본 상태로 넘어가지 않는다.
   - 로그 · 수치: 실측값을 §3에.
6. 검증이 전부 통과하면 §1 상태 `검증 완료`. 안 되면 `구현 완료`로 두고 무엇이 안 됐는지 §5에 적는다.
7. 코드와 do 문서를 커밋한다. 메시지에 배치 id를 넣는다(예: `do: B2 가사 오프셋 보정 + 테스트`).
8. 플레이스홀더 · TODO · 빈 핸들러를 남기고 다음 배치로 가지 않는다.

## 3. 질문 파일

다음 중 하나면 만들고 **멈춘다.**
- design을 바꿔야 구현이 된다(데이터 구조 · 책임 배치 · 인터페이스 · 배치 검증 방법 자체).
- design이 답하지 않은 갈림길을 만났고, 어느 쪽이든 결과가 달라진다.
- design이 지목하지 않은 기존 테스트가 실패해 테스트를 고쳐야 통과한다.
- plan의 SC나 범위와 어긋나는 것을 발견했다.

파일: `docs/PDCA/v{major}/{stem}/{stem}.qN.md` (N은 §4 다음 번호).

```
# {stem} 질문 q{N}

## 막힌 것
{어느 배치에서, 무엇이, 왜}

## 선택지와 대가
- a: {내용} — {대가}
- b: {내용} — {대가}

## 추천
{하나와 이유}

## 답
(사용자가 적는다. 대화로 답해도 된다.)
```

답을 받으면:
1. design을 바꾸는 답이면 design.md 해당 절을 고치고 Version History에 `질문 q{N} 답 반영` 행. 이것이 do 세션이 design을 고치는 유일한 경우다.
2. 설계 범위 안 세부면 do §2 구현 결정에 적는다.
3. do §4 질문 이력에 `q-N / 요지 / 결론 / 반영 위치` 한 줄.
4. 질문 파일을 지운다. 커밋. 배치 루프로 돌아간다.

## 4. 세션 종료

- §5 진행 로그에 "종료: 끝낸 것, 남은 것, 다음 세션 주의점".
- 헤더 갱신일. Version History 행(`세션 N`, 계기 "배치 B-x~B-y").
- 커밋 · 푸시. RULE.md에 CI 확인 명령이 있으면 실행해 결과를 §5에 한 줄.
- §1 전 배치가 `검증 완료`면 헤더 상태를 `완료`로 바꾸고 "모든 배치 검증 완료. 다음은 새 세션에서 `/pdca-close`"라고 보고한다. 아니면 남은 배치와 다음 `--scope`를 보고한다.

## 하지 않는 것

- design을 고치지 않는다(질문 답 반영 제외). plan을 고치지 않는다. 검증 기준을 고치지 않는다.
- 검증 없이 다음 배치로 가지 않는다. 사용자 육안이 필요한 배치를 확인 없이 `검증 완료`로 찍지 않는다.
- 테스트를 끄거나 건너뛰지 않는다. design이 지목하지 않은 테스트를 고치지 않는다.
- 범위 밖 결함을 고치지 않는다. §5 진행 로그에 적어 두면 close가 report §3.4로 보낸다.
- 통합 브랜치에 머지하지 않는다. `main`을 건드리지 않는다. 백로그를 바꾸지 않는다.
- plan · design을 do 문서에 재진술하지 않는다.
